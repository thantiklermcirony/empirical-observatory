# Active Context: independent product review

Recommendation: first serve **developers resuming a coding-agent task after its code or environment has changed**. Their immediate problem is: “Which earlier conclusions still apply, and what must I rerun before trusting this patch?” Deliver a CLI/MCP tool that reads actual command results, repository state and runtime identities, then returns an evidence-linked continuation packet and the next useful check. This makes the existing ledger operational: it helps the agent complete work instead of merely recording work. Defer group-conversation memory until this workflow earns repeat use.

The hardest problem is **recovering complete applicability dependencies without asking users to annotate everything**. A passing test depends on code, command, environment, data, services and assumptions; a code hash alone is insufficient. Conversely, an unrelated documentation change should not invalidate everything. Natural-language explanations can invent dependency edges. Start with mechanically captured dependencies and explicitly unknown dependencies; measure inferred edges separately. Selecting the cheapest check that can alter a decision is harder than ranking vaguely relevant memories. A graph edge or model confidence score is not a measured value of information.

Reuse Graphiti for episodes, temporal relationships, typed entities and retrieval, with an adapter holding immutable tool receipts and explicit “supports”, “depends on” and “needs recheck” records. These are application-declared relationships, not scientific discoveries. Graphiti already provides temporal facts, source provenance, custom types and hybrid retrieval; its ingestion can require LLM/embedding calls, so include those costs. Keep the refresh policy independently replaceable and compare with ordinary Graphiti retrieval plus fixed refresh. [Graphiti documentation](https://github.com/getzep/graphiti)

Do not make Graphiti mandatory for the first diagnostic. Use structured receipts and existing local storage to test the policy cheaply. Known dependency invalidation already has strong conventional implementations: Bazel caches actions using declared inputs, commands and environment information. A content-addressed dependency baseline is essential; outperforming “remember an old sentence forever” would establish little. Attestor also already offers temporal retrieval, provenance and budgeted context assembly. [Bazel](https://bazel.build/remote/caching), [Attestor](https://github.com/bolnet/attestor)

**Cheap first go/no-go:** freeze 30 runnable continuation episodes across at least five small public repositories, held out by repository. Include relevant code changes, configuration/dependency changes, unchanged reruns and irrelevant edits. Hidden executable assertions determine whether the proposed action is correct. Give every policy the same observable state and allowed checks, never the hidden dependency oracle. Compare rerun-all, fixed TTL, content/dependency invalidation and a fixed-budget refresh policy. Record stale-success claims, completed decisions, abstentions and total checking/ingestion time. Keep timeouts and failures in the denominator. Proposed engineering gate: no false “still verified” claims on these episodes, unchanged completion versus rerun-all, and at least 20% lower checking cost than the strongest equally correct conventional policy. Freeze thresholds before execution; this small gate is not a reliability guarantee.

That no-LLM diagnostic can reject a weak architecture cheaply, but cannot establish improved agent performance. Next, use one fixed agent and untouched ToolSandbox scenarios before a separately labelled changing-world extension. Its default simulated users require API access, some tools require RapidAPI, and LongMemEval's published answer evaluator uses an API model; neither is automatically a free local benchmark. No execution or spending is proposed here. [ToolSandbox execution/evaluation](https://github.com/apple/ToolSandbox), [LongMemEval evaluation](https://github.com/xiaowu0162/LongMemEval)

Stop or simplify if gains vanish against dependency invalidation, disappear after ingestion cost, or require manually supplying the dependencies the product promises to discover. A useful first release should eliminate a real repeated rechecking burden, even if the winning policy is conventional.
